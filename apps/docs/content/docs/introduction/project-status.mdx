## Maturity at a glance

These terms are not interchangeable; each is earned by specific evidence. The full definitions are in the
[communication and maturity terminology guide](https://github.com/tobin-protocol/tobin/blob/main/docs/COMMUNICATION-AND-MATURITY-TERMINOLOGY.md).

| Level | Status |
|---|---|
| Implemented | Yes: MVP-1.2 to MVP-1.5 and wallet-first authentication. |
| Tested | Yes: automated suites, contract tests and real-browser journeys. Same-author tests. |
| Testnet-verified | The settlement path, narrowly: one owner-run execution of eight transactions with multisig co-signing, read back from the network and compared with the approved plan. Not the whole project; wallet-first sign-in is not Testnet-verified. |
| Independently reviewed | No. All reviews and evidence are by the implementing author. |
| Pilot-ready | No. It depends on MVP-1.6 to MVP-1.8 and an independent security review. |
| Production-approved | No. The release gates for versioned and production releases are blocked ([`release/RELEASE-GATES.json`](https://github.com/tobin-protocol/tobin/blob/main/release/RELEASE-GATES.json)). |

A Testnet demonstration is evidence about the mechanics in a stated scope. It is not evidence of production behaviour.

the real Stellar Testnet.

## What is and is not connected

The persisted application records stop at *execution preconditions*. The settlement and execution records never read
from or submit to the network. Real on-chain execution is performed by separate, owner-run tools that keep their own
run log, and confirmed outcomes are **not** written back into the application&apos;s records.

## Not implemented

Account recovery for wallet-only users; deadlines, abort, default and recovery handling, collateral and Merkle
commitments (the broader protocol design, not part of the approved roadmap); hardware-wallet or second-wallet
validation; any Mainnet capability; independent security review.

## Current scope and remaining engineering work

These remain visible because they are true, and because they are the validation requirements between a working Testnet
integration and a pilot.

1. **Wallet validation.** Freighter in Microsoft Edge produced authorization-entry signatures in the MVP-1.5 owner
   validation. The wallet-first sign-in flow itself has not yet been validated with the real extension; automated browser
   tests use a protocol-compatible stand-in. No second wallet or hardware wallet has been validated.
2. **Independent review.** No independent security review or fuzzing has been done. Evidence is same-author, from one
   environment and one browser engine.
3. **Migration 8** was tested on fresh databases and a populated version-7 test database, not on a real operator
   database.
4. **Account recovery** is deferred. A user must keep access to at least one verified wallet; there is no administrator
   or support override.
5. **Application-level reconciliation.** Confirmed on-chain outcomes are not yet written back to the application&apos;s
   records.
6. **Measured behaviour.** The Testnet settlement was a single one-base-unit execution. Maximum-size sessions, fee
   breakdown and measured resource use have not been validated.
7. **Repository controls.** The ruleset on `main` requires a pull request with one approving review but **no specific CI
   check**, and administrators can bypass it. That CI must pass is project policy, not something GitHub enforces.

The authoritative records are the milestone closure documents under
[`docs/product/architecture`](https://github.com/tobin-protocol/tobin/tree/main/docs/product/architecture). See also the
[roadmap](/docs/resources/roadmap).
