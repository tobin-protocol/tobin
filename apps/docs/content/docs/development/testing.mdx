Tobin uses layered automated tests across its smart contracts, TypeScript SDK, web console, and browser user journeys.

## Test layers

| Layer | Command | Notes |
|---|---|---|
| TypeScript type check | `npm run typecheck` | All workspaces, including the documentation app. |
| SDK tests | `npm test --workspace tobin-mvp1-sdk` | `node:test` suite; uses the Rust development bridge to avoid skips. |
| Console unit, integration, security and persistence tests | `npm test --workspace tobin-web-console` | Real SQLite; bridge-backed tests are skipped without `TOBIN_BRIDGE_EXE`. |
| Contract tests | `cd contracts && cargo test --locked --workspace` | Native host tests; also run against compiled Wasm in integration workflows. |
| Release-scan rule tests | `node --test scripts/release/scan.test.mjs` | The repository source scan validating release gate G09. |
| Documentation checks | `npm run validate --workspace tobin-docs` | Validates frontmatter, navigation, internal anchors, and repository links. |
| Browser journeys | From `apps/web-console`: `TOBIN_WIDTH=1200 node test/browser/<journey>.mjs <output dir>` | Driven over Chrome DevTools Protocol; requires a production build (`npm run build:console`). |

## Running a single test file

Node 24 executes TypeScript test files natively without a separate compilation step.

### Web console tests

Run any single test file from the repository root:

```bash
node --test apps/web-console/test/guards.test.ts
node --test apps/web-console/test/backend-security.test.ts
```

For tests that require the Rust development bridge (such as `console.test.ts`), provide `TOBIN_BRIDGE_EXE`:

```bash
TOBIN_BRIDGE_EXE="$PWD/contracts/target/debug/examples/bridge" node --test apps/web-console/test/console.test.ts
```

On Windows PowerShell:

```powershell
$env:TOBIN_BRIDGE_EXE = "C:\path\to\tobin\contracts\target\debug\examples\bridge.exe"
node --test apps/web-console/test/console.test.ts
```

### SDK tests

Run individual SDK test files directly:

```bash
node --test packages/mvp1-sdk/test/engine.test.ts
node --test packages/mvp1-sdk/test/primitives.test.ts
```

To run cross-language bridge tests in the SDK:

```bash
TOBIN_BRIDGE_EXE="$PWD/contracts/target/debug/examples/bridge" node --test packages/mvp1-sdk/test/interop.test.ts
```

### Contract tests

Run a specific contract test integration file from the `contracts` directory:

```bash
cd contracts
cargo test --locked -p tobin-clearing-v1 --test lifecycle
cargo test --locked -p tobin-clearing-v1 --test settlement
```

To run a single test function within a test file:

```bash
cargo test --locked -p tobin-clearing-v1 --test lifecycle create_admits_the_creator
```

## Browser journeys catalogue

Browser journeys in `apps/web-console/test/browser/` execute against a production Next.js instance using a headless Chromium browser over the Chrome DevTools Protocol (CDP).

Each journey verifies user interactions, state persistence, error boundaries, and visual layouts. Run them at both desktop (`TOBIN_WIDTH=1200`) and mobile (`TOBIN_WIDTH=420`) viewport widths.

| Journey | Script / npm invocation | What it proves | Typical duration | Prerequisites |
|---|---|---|:--:|---|
| **Local Sandbox** | `node test/browser/journey.mjs`<br/>`npm run test:browser --workspace tobin-web-console` | Full lifecycle of the local sandbox (`/`) against real contracts via the bridge: minting, session creation, obligation submission, netting calculation, and atomic settlement. | ~15 s | `npm run build:console`, `TOBIN_BRIDGE_EXE`, browser |
| **W0 Console** | `node test/browser/w0-journey.mjs`<br/>`npm run test:w0-browser --workspace tobin-web-console` | Mock-adapter console (`/w0`): scenario switching (`ok`), development IDP sign-in, session navigation, participant and obligations tables, and mock approval flows. | ~8 s | `npm run build:console`, browser |
| **Sessions Experience** | `node test/browser/sessions-journey.mjs`<br/>`npm run test:sessions-browser --workspace tobin-web-console` | Institutional sessions view (`/sessions`): session lists, filtering, draft creation, participant management, and CDP error interception handling. | ~10 s | `npm run build:console`, browser |
| **Settlement Preparation** | `node test/browser/settlement-journey.mjs`<br/>`npm run test:settlement-browser --workspace tobin-web-console` | Settlement preparation (MVP-1.4): batch creation from approved calculations, instruction validation, reviewer approval and rejection, and SQLite persistence across server restarts. | ~12 s | `npm run build:console`, browser |
| **Authorization** | `node test/browser/authorization-journey.mjs`<br/>`npm run test:authorization-browser --workspace tobin-web-console` | Institutional authorization (MVP-1.3): reviewer grants, separation of duties, immutable decisions, automatic invalidation upon data edits, and tenant isolation. | ~10 s | `npm run build:console`, browser |
| **Clearing Operations** | `node test/browser/clearing-journey.mjs`<br/>`npm run test:clearing-browser --workspace tobin-web-console` | Clearing operations: organization onboarding, session creation, obligation entry and editing, deterministic calculation snapshotting, and calculation staleness checks. | ~12 s | `npm run build:console`, browser |
| **Backend Foundation** | `node test/browser/backend-journey.mjs`<br/>`npm run test:backend-browser --workspace tobin-web-console` | Core application backend: user registration, HttpOnly cookie sessions, organization creation, invitations, roles (`admin`, `member`), and session expiry across server restarts. | ~10 s | `npm run build:console`, browser |
| **Wallet Authentication** | `node test/browser/wallet-auth-journey.mjs` | Wallet-first authentication and onboarding: wallet challenges, SEP-53 message signing via injected Freighter stand-in, returning user sign-in, and account/network switching. | ~14 s | `npm run build:console`, browser |
| **Sticky Badge Check** | `node test/browser/badge.mjs` | Verifies live sticky positioning of the "LOCAL SANDBOX" badge during page scrolling at short viewports (height 500 px) for 1200 px and 420 px widths. | ~4 s | `npm run build:console`, `TOBIN_BRIDGE_EXE`, browser |

<Callout type="info" title="Browser discovery on Linux and macOS">
  On Linux and macOS, the CDP test driver requires setting `TOBIN_BROWSER` to the path of your installed Chromium binary
  (for example, `export TOBIN_BROWSER=$(which google-chrome || which chromium)`).
</Callout>

## Skipped tests

Without `TOBIN_BRIDGE_EXE`, tests that require the Rust development bridge are **skipped, not passed**.

- **SDK suite:** Reports 9 skipped tests without the bridge (8 bridge tests and 1 intentional skip for attribution-pending intent fixtures). With the bridge, exactly 1 test is skipped.
- **Web console suite:** Reports 8 skipped tests without the bridge (`console.test.ts`). With the bridge but without a production build, 2 tests skip (`next-server.test.ts`). With both the bridge and a production build, 0 tests skip.

Always report test skip counts alongside passing counts in pull requests.

For setup instructions and the full breakdown, see [Local environment setup](/docs/development/local-environment#interpreting-test-skips-and-results) and [Troubleshooting](/docs/development/troubleshooting).

## Hosted CI is not local validation

On pull requests, hosted CI executes:
- Rust formatting check and locked workspace tests
- Bridge build and TypeScript typecheck
- Web console and landing page production builds
- SDK tests and Console unit/security tests with the bridge
- Dependency baseline and documentation link checks
- Release gate scanner tests
- The W0 mock browser journey (`w0-journey.mjs`), through the `w0-console.yml` workflow, which runs only when the pull request touches the paths that workflow lists

Most other browser journeys (`journey.mjs`, `sessions-journey.mjs`, `settlement-journey.mjs`, etc.) are **not** run on pull requests. Run the journeys relevant to your changes locally before opening a pull request.

## What a test proves

A passing test proves only what it asserts. When implementing fixes or new capabilities, write tests that would have detected the bug, and never weaken assertions to achieve a passing status.
