## 2. How authorization validation works

For each operation the approved transaction requires **exactly one** authorization entry. `validateAuthorizationEntries` (`authorization.cjs`):

1. Derives the expected entries (section 3). It does not look at the simulation to decide what is expected.
2. Requires a list of exactly the expected length. Fewer is "missing", more is "unexpected additional" or, when the extra entries repeat one another, "duplicate". Because exactly one entry is approved there is no accepted ordering of several entries, so a reordered or padded set is simply an extra entry and is refused. (The specification has no ordered multi-entry case; if one is ever added it needs its own specification.)
3. Decodes each entry strictly with the pinned SDK's XDR types from an XDR object, base64 text or bytes, and requires it to re-encode to the same bytes. Anything that does not decode, has trailing data, or is not canonical is refused ("cannot be decoded").
4. Requires the credential kind to be `sorobanCredentialsSourceAccount` (the transaction source, already pinned to F by `verifyTransaction`). Address credentials, address V2, address with delegates, and any unknown kind are refused. (There is no "pre-authorized transaction" credential in Soroban authorization; any such arm would be an unknown kind and refused.)
5. Layers 1 and 2, `structuralCompare`: builds a canonical description of the entry's invocation tree with explicit, fail-closed checks, and compares it field by field with the description of the expected entry, reporting the first differing path (for example `fn.args[1]`).
6. Layer 3, `bytesCompare`: requires the entry's canonical XDR to equal the expected entry's canonical XDR byte for byte.

The two comparison layers are separately exported and separately tested, so neither hides behind the other.

## 3. How the expected entries are derived

From the same pinned configuration that builds the transaction (`cfg`): the admin F, the salt, the Wasm hash, the predicted token contract ID, the metadata and cap, the recipients C and D and the amounts.

| Operation | Expected entry |
|---|---|
| `deploy` | one `SourceAccount` entry; root function `CreateContractV2HostFn` with preimage `fromAddress` (deployer F, the pinned salt), executable `Wasm` (the approved hash) and the five constructor arguments (minter F as an address, cap as i128, decimals as u32, name and symbol as strings); no sub-invocations |
| `mint-C` | one `SourceAccount` entry; root function `ContractFn` on the predicted token contract, function `mint`, arguments (address C, i128 20,000); no sub-invocations |
| `mint-D` | as `mint-C` with address D and i128 10,000 |
| any other name | no specification exists; the operation stays blocked |

**Evidence that the derivation matches reality** (`auth-evidence.cjs`, read-only): the derived deploy entry is byte-identical to the entry returned by a **live protocol-30 simulation** of the exact deploy operation (a funded test account used as a stand-in deployer, never signed), and the derived mint entry is byte-identical to the entry of the **real on-chain governed-token mint** (same Wasm, protocol 29). Both real entries are stored as public fixtures and checked by a test. **Not observed:** a mint entry produced by a protocol-30 simulation against the not-yet-deployed TST contract. If it differed, the signer would refuse and a person would have to review the difference.

## 4. How nested invocations are validated

`describeInvocation` walks the tree recursively (depth limit 8). At each node it requires exactly the fields `function` and `subInvocations`, a list of sub-invocations, and a supported function kind (`ContractFn` or `CreateContractV2HostFn`; the legacy create-contract kind and every unknown kind are refused). It returns the node's canonical description together with the descriptions of all sub-invocations. The expected tree has no sub-invocations, so any nested call, however deep or however similar to the root (even an identical copy), changes the description and is refused; deeper chains are refused by the same rule or by the depth limit. Arguments are limited to the four value types the approved calls use (address, i128, u32, string); every other ScVal type is refused as unsupported, and values are compared as canonical strings (i128 as a decimal string, so 128-bit extremes and sign cannot alias).

## 5. How the BSTR cleanup works

`Read-TobinSecret` (embedded verbatim in the production script and tested as such):

1. `$bstr` starts as the null pointer.
2. Inside `try`, the BSTR is allocated (`SecureStringToBSTR`) and converted to text (`PtrToStringBSTR`), and the text is returned.
3. In the `finally` block, always: if a BSTR was allocated, it is zeroed and freed (`ZeroFreeBSTR`); in a nested `finally`, so that a failure of the free step cannot skip it, the `SecureString` is disposed. If the allocation itself failed, nothing is freed (nothing was allocated).

The three unmanaged operations are script-block parameters with the real calls as defaults so that the tests can substitute instrumented fakes. The secret still travels only through the stdout pipe; nothing is logged, written to disk or placed in a command line; errors stay generic. The managed plain-text string PowerShell returns, and the JavaScript strings in the parent process, cannot be erased on demand. A failure-injection test found a gap in the first version of this fix (a failing free step skipped the disposal); the nested `finally` closes it.

## 7. Mutation results

Command: `node mutate.cjs`. The harness first runs all seven test files and **aborts unless the baseline is green** (baseline: 142 passing, 0 failing). Each mutant weakens exactly one rule in the source and is then run against the offline suites (fast) or the Windows suites (win); a mutant is *killed* when at least one test fails.

**Final run: 130 mutants attempted, 130 killed, 0 surviving or not applied.**

No mutant survived and none failed to apply.

Of these, 39 target the authorization module and its two call sites in the core (entry count, duplicates, credential kinds, canonical encoding, depth, field checks, contract and function kinds, deployer, salt, Wasm hash, function name, argument lists and each value type, nested invocations, both comparison layers, the comparison helper, the expectation for each operation, and each of the two integration points) and 9 target the BSTR cleanup (free removed, free when nothing allocated, disposal removed, disposal skipped on a failing free, non-zeroing free, wrong conversion call, allocation moved outside the protected block, trailing-newline trim, buffer zeroing). The remainder are the revision-3 and revision-4 mutants, re-run against the current source.

History of this revision: the first complete run (before the survivor fixes) attempted 129 mutants with 5 surviving or not applied; they were analysed, tests were added or code simplified, and the whole harness was re-run from scratch to produce the final figures above. Details:

**First complete run (129 mutants): 124 killed, 4 survived, 1 definition was stale.** Each was analysed:

| Result | Mutant | Cause and action |
|---|---|---|
| survived | non-canonical encoding accepted (the re-encode check) | A **test gap**, not an equivalent mutant. An experiment showed the SDK's decoder tolerates non-canonical base64 text (trailing newline, inner whitespace, URL-safe alphabet, missing padding, non-zero trailing bits), so the re-encode check is a real control. A test with those forms was added |
| survived | contract-call fields not checked | Test gap: only the function level had an extra-field test. A plain-object test for the contract-call node (extra and missing field) was added |
| survived | other deployment preimage kinds accepted | Test gap: only a discriminant edit was tested (which fails in the decoder). A test with a `fromAsset` preimage was added |
| survived | value types not compared (in `firstDifference`) | The guard was **redundant**, and examining it showed that `firstDifference({}, null)` would have thrown a `TypeError`. The function was simplified to one guard that handles null, primitives and mixed shapes; exact-answer tests and three new mutants were added |
| not applied | original authorization-type check | The mutant targeted the old credential loop that this revision removed; it is replaced by "any credential kind accepted", which is killed |

After these fixes the **entire harness was re-run from scratch** on the final source, with the result reported above.

**Not mutation-tested (unreachable):** the two entry-level `requireKeys` calls in `validateAuthorizationEntries` (on the decoded entry and on its credentials). They run on objects produced by the strict XDR decoder, whose shape is fixed, so a mutant removing them would be equivalent; they are kept as defence in depth against a future SDK that adds a field.


## 8. Remaining limitations (nothing here is claimed as verified)

- **No real signing or submission has ever been validated.** The real DPAPI blob and key do not exist; the production decrypt script has run only against dummy blobs.
- **Mint authorization at protocol 30 is unobserved** (the TST contract does not exist). The expected mint entry is confirmed against a real protocol-29 mint of the same Wasm only; the mint footprint and resources are also unobserved at protocol 30.
- The validator is only as good as the specification it derives from: the specification says "one `SourceAccount` entry, no sub-invocations". If Soroban ever records additional entries for these calls on a future protocol version, the signer will refuse until a person updates the specification.
- The expected entries and the host function come from the same configuration, so a wrong configuration would be wrong in both. The configuration pin (see revision 4) addresses that, and is not an independent boundary until its hash is preserved outside the signer's directory.
- Two entry-level field checks in `authorization.cjs` (`requireKeys` on the decoded entry and on its credentials) cannot be reached with real decoded XDR; they are defensive (a future SDK that adds a field would be refused) and are therefore not mutation-tested (section 7).
- The command-line wrapper's success path has never been run; only its refusal paths have.
- Stored fixtures contain a stand-in test account's public address and real public XDR; they contain no secret.
- Independent review of this package is still required; this review was written by the author of the code.

## 9. Reconstructing the signer

Every file is stored with a `.txt` suffix and the same relative path as the original. To rebuild, remove the `.txt` suffix from each file (`test/` and `test/fixtures/` keep their layout), place the folder as the scratchpad's `tst-signer/` next to a `pk/x-stellar-stellar-sdk-17.4.0/package` folder holding the unpacked `@stellar/stellar-sdk` 17.4.0 npm package (the loader checks its version and the SHA-256 of `dist/stellar-sdk.js`), and use Node 24.14.0 on Windows. Run:

```
node --test test/tst-signer.test.cjs test/hardening.test.cjs test/submission.test.cjs test/expiry.test.cjs test/authorization.test.cjs test/windows.test.cjs test/dpapi-cleanup.test.cjs
node mutate.cjs
```

`SHA256SUMS.txt` lists the original file names and their SHA-256 (each `.txt` copy has the same hash as its original). The scripts `evidence.cjs`, `dryrun-live.cjs`, `auth-evidence.cjs` and `auth-probe.cjs` make read-only network queries and read a local public-address file; they are evidence tools, not part of the signer or of the test run.
