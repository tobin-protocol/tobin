# MVP-1.5 wallet and signing

## Three distinct concepts (kept apart in code and UI)
1. **Authenticated Tobin user**: a local account with a server session.
2. **Institutional role and authorization**: administrator, reviewer capability, decisions bound to calculations and batches.
3. **Stellar account and signing capability**: control of a key.
Connecting a wallet, verifying a key and holding an institutional role are different acts. A verified key grants no role, no reviewer capability and no signing authority in Tobin (tested: a verified member remains unable to approve or prepare). A reviewer does not become a signer, and a signer does not become a reviewer. Removing a member removes their verification; the proof is not a permission that outlives the membership.

## Implemented: wallet ownership verification (no wallet needed)
Flow: `POST /orgs/:o/wallet-challenges {network, publicKey}` returns a one-time message; the key holder signs it **outside Tobin**; `POST .../wallet-challenges/:id/verify {signature, scheme}` verifies on the server. The message binds organization, user, network, public key, a 192-bit nonce, issue and expiry times (5 minutes) and states that it signs no payment. Server rules: the challenge must belong to the caller and organization, be unused and unexpired; every failure (unknown, someone else's, expired, used, wrong signature or scheme) returns one identical error; a successful use marks the challenge used (replay refused); a key already verified for another member of the organization is refused (409); the same member re-proving a key is idempotent. Schemes: `raw` (ed25519 over the message bytes) and `sep-53` (ed25519 over SHA-256 of `"Stellar Signed Message:\n" + message`, as understood here). Tested with throwaway keys made by `node:crypto`.
**Update: the SEP-53 message signature through Freighter was accepted by the server in the owner-run Stage 1 (scheme per the owner's recollection). The following sentence is the earlier state.** Earlier: not tested against any real wallet. Whether Freighter or another wallet produces exactly these bytes is unverified; the UI therefore asks for a pasted signature and states that Tobin does not connect to a wallet.

## Signing architecture (designed, not built)
Before any signature request the server would re-verify: the batch is approved and eligible; its calculation is current and approved; the fingerprint matches; the asset is canonical and supported; every payer and payee has a verified account on the batch network (the execution snapshot); the network passphrase is the intended one; the transaction's operations equal the approved instructions. The request would display destination, asset, amount, network and contract call for inspection; any change after approval requires revalidation and a new approval. A rejected or abandoned signature returns the execution to `awaiting-signer` and never marks it signed. Tobin never holds private keys and must not log secrets or signed envelopes. One person controlling several accounts is not independent multi-party control and must not be presented as such.

## Update: wallet connectivity and the unknowns (this execution)
- `@stellar/freighter-api` 6.0.1 and `@stellar/stellar-sdk` 17.4.0 are pinned in `apps/web-console`. The Freighter surface used: `isConnected`, `isAllowed`, `requestAccess`, `getAddress`, `getNetwork`, `signTransaction`, `signAuthEntry` (errors are returned in an `error` field, not thrown). Node 24 and a Chromium browser are required; Microsoft Edge is the validated environment.
- The Settlement tab has a wallet box: **Check wallet** reads without prompting; **Connect Freighter** requests access; a wallet is shown connected only if Freighter reports it, on Testnet, and the account is compared with the verified participant accounts. In a real browser without the extension it reports UNAVAILABLE (tested in the journey). Signing is not requested from the UI yet because no attempt reaches signing in this build; the signing wrapper exists and is unit-tested with a labelled mock wallet.
- AddressV2 (NETWORK-READ, protocol 30): the network returns `source_account` credentials for the transaction source and `address_v2` for other signers. The official SDK `authorizeEntry` handles V2. A multisig account can authorize only as the transaction source, via the envelope. Whether Freighter's `signAuthEntry` produces what `authorizeEntry` needs is **NOT VERIFIED**: that is step 6 of the owner validation.
- Ownership of a multisig account cannot be proven by one key's signature (a design gap, recorded in the contract compatibility document).
