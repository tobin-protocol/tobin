## Why the Testnet end-to-end was BLOCKED (historical: written before the owner-run stages; superseded by the 2026-11-07 execution recorded in MVP-1.5-TESTNET-VERIFICATION.md)
1. No funded, authorized participant accounts exist for this work; creating keys or funding accounts is new network activity that the standing workspace rule forbids without fresh explicit authorization, and the token cannot be minted by this work (its minter is the governed multisig).
2. No wallet is available in this session (W2 never ran a real Freighter), and the wallet's authorization-entry behaviour is unverified.
3. No Stellar SDK is a dependency, so transactions cannot be constructed or simulated.
4. The batch-to-contract mapping needs an owner decision (see the architecture document).
5. The protocol-30 `AddressV2` credential path is untested end to end; the Rust signer must not be reused for it.

## Decisions taken (implemented)
Obligations carry full asset identity (decision 1); a rejected batch may be prepared again from the same current approved calculation under attempt control (decision 2); operational closure needs an approved, still-eligible batch (decision 3). Details in the architecture, asset identity and instruction documents.

## Update (this execution): what the audit found after reading the real network
The first table above was written from the repository only. After read-only Testnet reads and installing the approved SDK (see `MVP-1.5-CONTRACT-COMPATIBILITY.md` and `MVP-1.5-TESTNET-VERIFICATION.md`): the Stellar SDK gap is closed (17.4.0 pinned); the contract gap is a lifecycle mapping, now implemented as the adapter; the Freighter gap is narrowed to one open item (AddressV2 `signAuthEntry`, owner-run); and three new facts bound any real settlement: the governed token's total supply is 1 base unit held by the administrative multisig, multisig accounts can authorize only through the transaction envelope, and key-signature ownership proof cannot cover a multisig account. No network write was performed.
