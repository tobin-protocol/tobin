# MVP-1.5 threat model (updated)

Same-author. **Not an independent audit.** Status: MITIGATED (implemented and tested), PARTIAL, UNRESOLVED, or N/A-YET (the capability that would be attacked does not exist in this build; the control is designed and must be verified when it is built). Severity is the impact if the threat succeeded on a real settlement. Evidence references: WO `wallet-ops.test.ts`, AO `attempts-ops.test.ts`, SP `stellar-plan.test.ts`, SR `stellar-rpc.test.ts` (MOCK wallet and network), SS `settlement-state.test.ts` (MOCK observations), SJ `settlement-journey.mjs`, NR = real read-only Testnet reads (`evidence/`).

| # | Threat and scenario | Sev | Mitigation | Evidence | Residual risk |
|---|---|---|---|---|---|
| 1 | Wallet impersonation: a user claims a key they do not hold | High | one-time challenge bound to org, user, network, key; server-side ed25519 verification; uniform failure; replay and expiry | WO; SJ | real wallet signature formats untested; a multisig account cannot be proven (UNRESOLVED) |
| 2 | Malicious or substituted transaction: the wallet or the page swaps destination, asset, amount or call | Critical | the plan is derived server-side from the approved batch; the signed answer must be the SAME transaction hash and carry a valid signature of the expected key; fingerprints at batch, instruction and plan level | SP; SR (MOCK wallet) | the real wallet prompt content is unverified; a compromised browser could still show the user something else (N/A-YET for signing in the UI) |
| 3 | Wrong network: signing or submitting on Mainnet | Critical | only `testnet` is accepted by the adapter; the wallet must report the Testnet passphrase or no signing request is made; assets and executions are network-bound | SP; SR; NR | enabling Mainnet needs separate validation (not enabled) |
| 4 | Replay: reuse of a signed authorization entry or a transaction | High | `validUntilLedger` bounded (10 ledgers policy for entries); a transaction hash belongs to one attempt step (schema UNIQUE); the on-chain session cannot be created twice | AO; NR (not exercised on chain) | failed-transaction authorization reuse until expiry (known, EQ-20 accepted) |
| 5 | Duplicate settlement: the same payment submitted twice | Critical | one live attempt; no path from unknown-outcome back to submission; one execution per batch; submission code sends exactly once and computes the hash first | AO; SR (MOCK) | the real network behaviour on duplicates is unverified |
| 6 | Stale approval: settlement after the data changed | High | invalidation in the same transaction as every change; derived status; an attempt needs an approved, eligible batch | SP; AO | none known |
| 7 | Batch mutation after approval | High | immutable by trigger; fingerprints; reviews name the fingerprint | SP | direct database access by an operator can still alter the file (operational control) |
| 8 | Unauthorized signer: someone signs for another participant | Critical | every signer enumerated per step; a signer must be a verified account of that participant; the initiator signs for no one else | SP | institutional meaning of "a participant" is account-based; one person with several accounts defeats independence (UNRESOLVED; pilot requirement) |
| 9 | Compromised frontend | High | server recomputes and enforces everything; attempt states have no HTTP setter; confirmation needs server-validated evidence | AO | a compromised browser can mislead the user at the wallet prompt |
| 10 | RPC response manipulation | High | the comparison recomputes nets from on-chain obligations; confirmation requires an independent read of a recorded hash; unknown stays unknown | SP; SS (MOCK) | a single RPC provider is trusted; a second independent source is not implemented |
| 11 | RPC outage or timeout | Medium | unavailable and not-found are unknown, never failed or confirmed; polling reads the original hash | SR (MOCK); NR (real NOT_FOUND read) | operators must resolve long-lived unknowns |
| 12 | Unknown transaction outcome leads to a second payment | Critical | see 5; a new attempt is refused until the outcome is established | AO | none known in logic; not proven on a real network |
| 13 | Private key exposure | Critical | Tobin never receives keys or seeds; the plan stores no secret; signed envelopes are not stored or logged; tests use throwaway in-memory keys | AO; release scan | users can paste anything; Freighter holds keys |
| 14 | Unauthorized token use or minting | Critical | no mint path exists in the application; the adapter spends only what a debtor authorizes; supply is 1 base unit and was not touched | NR (read only) | the governed multisig keeps mint authority (outside Tobin) |
| 15 | Contract authorization failure at settle | High | simulation before signing; settle is atomic on chain | NR (simulation of earlier steps) | `settle` itself was not simulated on a live session |
| 16 | Inconsistent database and chain state | High | confirmation only from a chain read; reconciliation requires a matching comparison; mismatch stops everything | SP; SS (MOCK) | no real settled session to test against |
| 17 | Incorrect asset mapping (classic vs token contract; Testnet vs Mainnet) | High | canonical identity; the adapter accepts only `testnet:contract:C...`; the session token must equal the batch asset | SP; SP policy tests | mapping a classic asset to its contract is unimplemented and unverified |
| 18 | Incorrect obligation mapping | High | one on-chain obligation per application obligation with the same id, parties and amount; nets compared independently | SP | untested on a live session |
| 19 | Multisig participant mishandled (single signature treated as authorization) | High | the plan documents source-account authorization for multisig; ownership of a multisig account is NOT claimed | doc | requires a signer-set aware proof before use |
| 20 | Owner-validation page misused to submit | Medium | it builds only unsubmitted, simulated material; it has no submit path | SJ step 8c | the owner could submit the material elsewhere on purpose |

Residual-risk summary: no real-network behaviour of signing, submission or settlement has been observed; the largest open risks are the unverified Freighter authorization-entry path, multisig ownership, single-provider RPC trust and account-based independence. Production hardening (key rotation and revocation of verified keys, rate limits on challenges, monitoring, a second chain reader, hardware-backed signing) belongs to MVP-1.7. No independent audit has occurred.
