# Key custody and recovery

Applies to the Testnet administrative multisig. Written before provisioning. Nothing here contains, or may ever contain, a key, seed or recovery phrase.

## Current custody model

- **All three signer wallets (founder, technical, security) are controlled by the founder.** The weights test the mechanics of weighted authorization. They do not provide independent approval, and a compromise of the founder's devices or backups compromises every signer.
- The dedicated administrative account has its own bootstrap (master) key, also generated by the founder outside the repository.
- The legacy deployer / token minter (`GD5ES…QNYPQ`) is a separate, older Testnet key. Its custody is unresolved: do not discard it. The legacy token can only be minted by it. Whether it is backed up is unknown; decide that before relying on the legacy token.

## Rules

1. Keys are generated on the owner's own device (hardware wallet preferred) and never typed into a chat, ticket, email, shell history, CI variable or `.env.example`. Claude Code is never given a seed.
2. Only public keys, signed transaction envelopes and transaction hashes are shared.
3. One physical backup per key, kept in a different place from the device. With one person holding all three wallets, keep each wallet's backup in a different location so that one theft or loss does not take all three.
4. The bootstrap key lives outside the repository, offline when not in use.
5. Before the bootstrap key is disabled, run a recovery drill (below) on Testnet.

## Failure cases

| Lost or compromised | Effect | Recovery |
|---|---|---|
| Founder key (5) | **Account frozen.** Technical + Security reach only 3 | Restore from the founder-key backup. If there is none, the account is unrecoverable and Testnet administration moves to a new account. This is the critical risk; decide the arrangement before disabling the master key |
| Technical key (2) | No signer changes (high needs it). Founder + Security (6) still do medium operations | Restore from backup; otherwise a new account |
| Security key (1) | Founder + Technical (7) still meet every category | Replace the signer (see `signer-management.md`) |
| Master key, still enabled | An extra weight-1 signer for an attacker | Remove it (weight 0) with Founder + Technical; do this promptly if it may be exposed |
| Any key suspected compromised | An attacker with only the technical or security key meets nothing alone; with the founder key, the account is exposed | Rotate immediately at the high threshold; if the founder key is the compromised one, move to a new account |

## Recovery drill (before the master key is disabled)

1. Confirm each signer's backup can restore the key on a clean device and sign a harmless low operation.
2. Confirm Founder + Technical can replace the security signer end to end and read the account back.
3. Record the date and result (public metadata only).

## Disabling the master key

Do not do it until the drill passes and the founder explicitly approves. If these conditions cannot be met, leave it enabled and document that the extra weight-1 path remains.

## Mainnet

Mainnet requires different custody: distinct people, distinct devices, hardware signing, and separate keys from every Testnet key. A single person holding all signers is not acceptable there.
